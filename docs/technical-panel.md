# Техническая панель INTERCITY

Панель встроена в NestJS backend и использует PostgreSQL. Она не использует учётные записи обычной Flutter-админки. Маршрут: `/api/technical/panel/` на домене API.

## Доступ владельца

При штатном развёртывании `scripts/vps_deploy_release.sh` создаёт первого технического владельца, только если технических аккаунтов ещё нет. Нет общего пароля по умолчанию. Пароль генерируется криптографически, в БД сохраняется bcrypt-хеш.

Первоначальные реквизиты передаются через файл `/opt/intercity/shared/technical-data/owner-access.json` с правами `0600`. Файл — временный канал передачи первоначального пароля, а не источник авторизации. Он не выводится в CI, не включается в Git или архив технических файлов при следующих деплоях.

На доверенном компьютере владельца с настроенным SSH-доступом к VPS:

```bash
umask 077
scp <ssh-user>@<vps-host>:/opt/intercity/shared/technical-data/owner-access.json ./intercity-technical-access.json
```

Если у SSH-пользователя нет прямого доступа к файлу, администратор сервера должен передать его владельцу через защищённый канал. Не публиковать файл в чате или логах. Открыть локально, сохранить реквизиты в менеджере паролей, войти в панель и в «Настройки правил и доступа» сменить свой пароль. После успешного входа с новым паролем удалить первоначальный файл на сервере и локальную копию. Не оставлять первоначальный пароль в незашифрованном архиве.

Для ручной первичной настройки на сервере:

```bash
docker exec intercity-backend node scripts/technical-owner.cjs
```

Команда отказывается перезаписывать существующие технические аккаунты. Пароль не печатается. Смена собственного технического пароля отзывает все технические сессии аккаунта.

## Разрешения

| Разрешение | Возможности |
| --- | --- |
| `events` | Обзор, события, проблемы, метаданные файлов, уведомления |
| `personal` | ФИО, телефоны, персональные снимки событий, IP и клиентские сеансы |
| `originals` | Получение оригиналов; это отдельный доступ к чувствительным данным документа |
| `users` | Операции поддержки пользователей |
| `danger` | Допуск к чувствительным операциям совместно с профильным разрешением |
| `settings` | Правила, технические аккаунты и просмотр/проверка аудита |

Например, наблюдателю достаточно `events`. Специалисту поддержки — `events,personal,users,danger`; оригиналы выдаются отдельно. Полное управление первоначально есть у владельца. Обычный JWT пользователя/ADMIN не открывает технический API. Все проверки выполняются сервером.

Авторизация использует случайную серверную сессию: в БД только SHA-256 токена, в браузере HttpOnly/SameSite=Strict cookie, в production Secure, срок 8 часов. Изменение записи технического сотрудника отзывает его сессии. Есть ограничение перебора входа и повторной проверки пароля. Изменяющие запросы требуют специальный заголовок и проверку origin; это не API для произвольного cross-site вызова.

## Рабочие разделы

1. **Обзор системы:** реальные проверки SQL и записи/удаления пробного файла, свободное место файловой системы, память процесса, uptime, счётчики ошибок и проблем. Время проверки видно на экране; обзор обновляется раз в 30 секунд при открытом разделе.
2. **Проблемы и ошибки:** группировка повторений с сохранением отдельных событий, первое/последнее появление, участники, ответственный, комментарии, предположение и подтверждённая причина. Закрытие требует результата проверки и исправляющей версии. Повторение после закрытия возвращает проблему в «Новое».
3. **Действия пользователей:** запросы, результаты, отказы, HTTP-код, длительность, версия, сеанс и связи. Есть поиск, фильтры и страницы по 50 записей; API допускает максимум 100.
4. **Пользователи и организации:** карточки реальных пользователей и профилей водителя. В проекте нет модели организаций пользователей — панель это явно сообщает.
5. **Безопасность:** повторные отказы входа/доступа по настраиваемому окну. Агрегация по сетевому адресу не устанавливает личность. Срабатывание — основание проверки, не доказанное нарушение.
6. **Отклонения процессов:** факты из существующего `TripVerification` со статусом REVIEW и его причинами; сканирование каждые 30 секунд, пакет до 100 записей с последовательным обходом. Техническая карточка не изменяет вознаграждение поездки.
7. **Файлы:** точная связь с requestId загрузки, размер, MIME, SHA-256, результат и версия проверки, оригинал целиком и увеличение. Текущие документы объекта отделены от файлов конкретного действия.
8. **Сервисы и фоновые задачи:** реальные доступные метрики технического обслуживания, состояние сбора и доставки push. Для остальных задач без общего источника явно указано отсутствие данных.
9. **Резервные копии и развёртывания:** отчёты, поступившие из штатного скрипта; отсутствующие исторические отчёты не восстанавливаются предположениями.
10. **Уведомления:** отдельные записи получателей, подтверждение, переход в проблему, Web Push. Одинаковая открытая проблема объединяется в одно уведомление получателя; отдельные события продолжают сохраняться. После повторного открытия уведомление активируется снова. Приглушение не подавляет критические события.
11. **Настройки:** правила качества, сроков хранения и повторных отказов, доступ сотрудников, смена своего пароля, просмотр и проверка контрольной цепочки аудита.

## Поддержка пользователя

В карточке пользователя доступны блокировка, разблокировка, отзыв сеансов и установка временного пароля. Для выполнения нужны `users` + `danger`, причина от 5 символов, подтверждение и действующий пароль технического сотрудника. Старый пароль нигде не показывается.

Каждая операция повышает `User.authVersion` и удаляет refresh-токены. JWT проверяется по текущей версии и блокировке на каждом новом авторизованном запросе. Открытые realtime-соединения пользователя закрываются в текущем экземпляре API. В текущем production один экземпляр backend; для нескольких экземпляров потребуется общий канал отзыва соединений.

При входе с временным паролем основной Flutter-клиент требует его сменить. Пока пароль не заменён, сервер запрещает бизнес-запросы, разрешая проверку аккаунта и смену пароля. Пользователя, который входит через отдельный старый административный экран, следует направить на обычный экран входа основного приложения для обязательной смены.

## Сбор событий и границы достоверности

- Middleware сохраняет START до бизнес-обработки, PROCESSING после успешной авторизации, FINISH/ABORTED по завершению HTTP. Незавершённая запись не доказывает, что пользователь прекратил работу: процесс мог завершиться аварийно, соединение пропасть или сбор отказать.
- Идентификатор обращения создаётся сервером и возвращается в `X-Request-ID`. Данные сеанса/платформы/версии и переходы экранов помечены как сообщённые устройством. Технический журнал не определяет личность по IP.
- Основной мобильный клиент передаёт случайный идентификатор текущего сеанса и безопасную категорию открытого экрана без query-параметров, адресов и реферальных кодов. Отдельный endpoint поддерживает ограниченные сообщения об открытии формы и повторной попытке. Не каждый локальный клик инструментирован.
- Сервер связывает пользователя после фактической авторизации, объект — по параметрам маршрута и допустимым идентификаторам серверного результата. Для профиля водителя фиксируются разрешённые изменения статуса/модели. Произвольные тела запросов и ответы не архивируются; полный универсальный diff всех таблиц не реализован.
- GPS в технический журнал не копируется: отдельного подтверждённого источника согласия на такой сбор нет. Существующий процесс проверки поездок продолжает работать со своими данными.
- Подробности ошибок очищаются от распространённых форм токенов, паролей, cookies, URL и длинных номеров. Заголовки авторизации, тела запросов и приватные ключи не записываются. Автоматический regex не заменяет запрет добавлять секреты в новые сообщения бизнес-кода.
- Консольные ошибки `console.error` попадают в отдельные системные события с очищенным сообщением. Не все сторонние библиотеки и фоновые исполнители используют этот канал; тотальная трассировка всех внешних систем не заявляется.

## Файлы и проверка качества

Новые загрузки документов водителя ограничены 10 MiB, одним файлом и 40 млн пикселей декодирования. Поддерживаются JPEG/PNG/WebP; повреждённые файлы, другие форматы и многостраничные изображения отклоняются. Декодируемые отклонённые изображения сохраняются только в закрытом техническом хранилище и не записываются в утверждённые документы профиля. Для недопустимого/повреждённого формата оригинал не сохраняется — причина остаётся в событии.

Алгоритм `quality-v1` оценивает детализацию по дисперсии лапласиана уменьшенного изображения: почти однородные/крайне размытые изображения отклоняются, промежуточные направляются на ручную проверку. Низкое разрешение само по себе не означает отказ. Это не OCR и не гарантия читаемости; шумное изображение тоже может иметь высокий показатель детализации. Распознавание пересъёмки экрана не реализовано и прямо обозначается как не выполненное. Все документы профиля по-прежнему требуют штатной проверки водителя.

Новые оригиналы находятся в `TECH_STORAGE_DIR`, вне `/uploads`. При выдаче проверяются разрешение, существование, путь и SHA-256; просмотр записывается в аудит. Подстановка ID чужого файла обычным пользователем отклоняется. `/docs/complete` не позволяет присвоить чужую новую загрузку или произвольный URL.

Старые локальные документы профилей не приписываются новым событиям. Доступ к UUID-каталогам водителей в `/uploads` теперь проверяется сервером; техническая панель получает такие изображения через собственный защищённый endpoint. Старые внешние URL не импортируются и не загружаются сервером. У старых файлов автор/время загрузки и исходный результат проверки неизвестны.

По умолчанию события и неактуальные оригиналы хранятся 90 дней. Очистка пакетная каждые 30 секунд; текущие документы профиля защищены от удаления по сроку хранения. После удаления остаётся метаданная отметка об отсутствии оригинала. Удаление аккаунта очищает персональные снимки событий и удаляет его закрытые документы через существующую повторяемую задачу удаления файлов.

## Web Push

Владелец открывает «Уведомления» и нажимает «Включить браузерные уведомления». Требуются HTTPS, поддержка Service Worker/Push API и разрешение браузера. При первом старте сервер генерирует VAPID-ключи в закрытом хранилище; они сохраняются между релизами. При необходимости можно задать `TECH_VAPID_PUBLIC_KEY`, `TECH_VAPID_PRIVATE_KEY`, `TECH_VAPID_SUBJECT` через защищённую конфигурацию.

В системном уведомлении только общее сообщение и ссылка на техническую проблему, без ФИО/телефона/содержимого ошибки. Текст push сам по себе не даёт доступа: после перехода требуется техническая авторизация.

Worker доставки обрабатывает подписки активных получателей, сохраняет число попыток и повторяет ошибки с увеличивающейся задержкой до часа. Удаляются недействительные подписки по 404/410. Ответ провайдера означает отправку провайдеру, а не доказанную доставку на экран; получение сотрудник подтверждает в центре уведомлений. Работа при закрытой вкладке зависит от браузера, ОС, разрешений и сети. End-to-end доставка на реальные устройства требует отдельной проверки владельцем после подписки.

## Развёртывание, резервное копирование и восстановление

Штатный процесс: сверка источников установленной версии → резервная копия PostgreSQL и uploads → архив technical-data без первоначального файла пароля → миграции → сборка/переключение → API/БД и маркеры версий → первоначальный технический доступ при необходимости → фактические отчёты BACKUP/DEPLOYMENT.

`technical-data` расположен в `/opt/intercity/shared/technical-data`, монтируется в `/app/technical-data`, закрыт правами каталога `0700` и не раздаётся Caddy. Архив содержит оригиналы, `audit.key` и VAPID-ключи, поэтому должен храниться как секретный backup. PostgreSQL backup также содержит персональные сведения и хеши сессий. Проверка SQL-footer и читаемости архивов не является испытанием полного восстановления.

Восстановление выполнять администратору сервера в режиме обслуживания:

1. Остановить backend и исключить новые записи. Сохранить отдельный текущий backup для обратного отката.
2. Выбрать согласованный комплект БД, uploads, technical-data и версию приложения; проверить целостность архивов. Для первичного перехода старый backup может не содержать technical-data.
3. Восстановить PostgreSQL в чистую целевую БД по действующему регламенту проекта. Архивы файлов распаковать в отдельные каталоги, проверить состав и затем переключить shared-пути; не смешивать разные снимки молча.
4. Восстановить соответствующий `audit.key`, VAPID и оригиналы с правами доступа. Замена `audit.key` случайным новым ключом нарушит проверку старой цепочки.
5. Поднять совместимую версию backend, применяя только проверенные необходимые миграции. Отозвать старые технические и пользовательские сессии согласно плану восстановления.
6. Проверить вход, API/БД, оригиналы и контрольные суммы, цепочку аудита, очередь уведомлений и установленную версию. Сохранить акт/отчёт восстановления. После восстановления старого снимка сверить его с сохранённой внешней контрольной точкой аудита.

Панель не содержит произвольного SQL, командной консоли или кнопки восстановления production из браузера. Ручные отчёты обслуживания можно передать в `scripts/technical-report.cjs` через stdin на сервере; HTTP endpoint для подделки результатов backup/deploy отсутствует.

## Проверка аудита

Технические действия имеют последовательный HMAC-SHA256 с предыдущим хешем и каноническим JSON. Запись сериализуется транзакционной блокировкой PostgreSQL. Триггер запрещает UPDATE/DELETE записей аудита. В настройках доступны просмотр и проверка цепочки.

Для обнаружения удаления конца истории нужно периодически сохранять `head` и `checked` проверки за пределами этой БД/сервера. Администратор БД/хоста с полным доступом может отключить триггеры или получить ключ: это не внешнее неизменяемое хранилище и не защита от владельца инфраструктуры. Аудит автоматически по сроку не удаляется; его архивирование требует отдельного регламента.

## Проверки разработчика

```bash
cd backend
npm ci
npx prisma generate
npm run build
node --test test/*.test.js
```

Сквозной набор требует отдельной локальной БД с точным именем `technical_panel_test` и хостом `127.0.0.1`; тест отказывается работать с другим адресом. Подготовить её схемой `prisma db push`, установить append-only функцию/триггер из технической миграции. Не выполнять это на production. Указать URL через `TECH_TEST_DATABASE_URL`; пароль в команды общего журнала не помещать.

```bash
node --test test/technical-*.test.js
```

Для браузерной проверки отдельно установить Playwright и Chromium в тестовую среду, передать `TECH_BROWSER_TEST_MODULE` с путём к модулю Playwright. В текущем тесте Chromium ожидается `/usr/bin/chromium`. Без параметра браузерный сценарий не исполняется. Набор использует изолированное техническое хранилище в системном temp; его ключ нужно сохранять при повторных прогонах на той же тестовой БД. Тестовые аккаунты и записи не попадают в рабочую БД.

Сценарии: отдельный вход и CSRF, обычный JWT без доступа, разграничение прав, два разных пользователя, фото с деталями/однородное/недопустимый формат, чужой ID, точная связь файла с действием, незавершённая форма и повторы, оборванный поток, отзыв JWT, блокировка, временный пароль и смена, уведомления, отказ push-провайдера с повтором, недоступный оригинал, запрет изменения аудита, очистка секретов, Chromium и адаптивная ширина.

## Ограничения эксплуатации

- Панель использует тот же API и БД: полный отказ backend/БД может сделать недоступной и панель. Для независимого оповещения нужен внешний мониторинг. Отдельный браузерный мониторинг приложения пока не подключён и не имитируется.
- Нет исторических данных до внедрения; нет полного захвата локальных кликов и универсального diff всех сущностей, отдельного каталога организаций или тотальной трассировки сторонних компонентов.
- Ресурсы относятся к процессу/доступной среде исполнения, а не полноценному мониторингу всего VPS. Показатели ОС могут отражать хост, а не квоты контейнера.
- Нет OCR, надёжного определения пересъёмки экрана, антивирусного движка или гарантии читаемости документа.
- Промышленная доставка Web Push требует разрешения и проверки на целевых устройствах. При отсутствии разрешения внутренние уведомления остаются в БД.
- Сбой БД может помешать самой записи события. Счётчик таких сбоев относится к текущему процессу; это не гарантия абсолютно полной истории при аварии.
- Отдельный результат неуспешного деплоя, завершившегося до запуска нового backend, может отсутствовать в БД; подробности остаются в CI/VPS. Успешные отчёты не следует трактовать как историю всех прежних попыток.

Эти ограничения отображаются в соответствующих разделах или описаны здесь; недоступные источники не заменяются вымышленными значениями.
