# InterCity × Kaspi.kz — API пополнения баланса водителя

Дата: 12.11.2026. Формат: JSON, UTF-8. Валюта: KZT.
Основание: предоставленный «Протокол взаимодействия (онлайн)».

## 1. Адрес и назначение

Единая точка подключения банка:
https://api.intercity.89-207-255-27.sslip.io/api/payments/kaspi

Метод GET, HTTPS, порт 443. Операции: command=check и command=pay.
Это пополнение баланса водителя через услугу в Kaspi.kz «Платежи», не Kaspi Pay/QR и не эквайринг Kassa24.
JWT пользователю банка не требуется. Доступ ограничен исходными IP банка на Caddy и в приложении.
Не вызывайте pay из мобильного приложения или браузера пользователя.

## 2. Реквизиты подключения

account: номер телефона водительского аккаунта без «+», пробелов, скобок и дефисов.
Регулярное выражение: ^7[0-9]{10}$ (строго 11 цифр).
В базе телефон хранится как +7XXXXXXXXXX. Пример преобразования: +7XXXXXXXXXX → 7XXXXXXXXXX.
Пассажир без профиля водителя, отсутствующий кошелёк или заблокированный пользователь не принимаются.
Пополнение только денежного баланса KZT; RUB, бонусный и реферальный балансы не меняются.
Сумма: от 0.01 до 10000000.00 KZT, ровно два знака после точки. Комиссия со стороны InterCity в этом API не удерживается.

Исходные IP согласно предоставленному PDF:
• 194.187.247.152
• 194.187.245.108
• 197.187.244.108
Последний адрес перенесён дословно; банк должен подтвердить его при подключении. Не заменять автоматически на похожий адрес.
Запросы с других IP: HTTP 403. Подмена X-Forwarded-For не даёт доступ.
Все ответы API имеют Cache-Control: no-store; GET pay никогда не кэшировать.

## 3. Параметры

command — обязательно; строка check или pay.
txn_id — обязательно; строка из 1–18 цифр, не преобразовывать в JavaScript Number. Ведущие нули сохраняются.
account — обязательно; 11 цифр в формате выше.
sum — для pay обязательно; строка, например 500.00. Для check фиктивна и полностью игнорируется, включая отсутствие/формат/значение.
txn_date — для pay обязательно; 14 цифр YYYYMMDDhhmmss, существующая календарная дата и время. Исходное значение хранится для сверок, не заменяется временем получения запроса.
data1…dataN — необязательные поля протокола; текущая реализация не использует их для идентификации или зачисления.
Для check и pay банк использует разные txn_id. pay не требует сохранённого check: кошелёк повторно проверяется в транзакции.
Часовой пояс учёта txn_date: Asia/Almaty (UTC+5); подтвердить при техническом согласовании с банком.

## 4. Проверка счёта — check

GET /api/payments/kaspi?command=check&txn_id=100000000000000001&account=70000000001&sum=200.00

Успех (HTTP 200):
{"txn_id":"100000000000000001","result":0,"comment":"Счёт доступен для пополнения","fields":{"field1":{"@name":"account","#text":"70000000001"},"field2":{"@name":"service","#text":"InterCity — баланс водителя"}}}

Неизвестный/заблокированный счёт (HTTP 200):
{"txn_id":"100000000000000001","result":1,"comment":"Счёт не найден или недоступен"}

check никогда не меняет баланс, не создаёт платёж и не требует авторизации водителя.
prv_txn_id и sum в ответе check отсутствуют.

## 5. Зачисление — pay

GET /api/payments/kaspi?command=pay&txn_id=100000000000000002&txn_date=20261112150000&account=70000000001&sum=500.00

Успех (HTTP 200), пример идентификатора провайдера:
{"txn_id":"100000000000000002","result":0,"comment":"OK","prv_txn_id":"1794488400000123456","sum":"500.00"}

prv_txn_id: уникальный сохранённый идентификатор пополнения провайдера, строка до 20 цифр. Значение примера не фиксировано.
sum в JSON возвращается строкой с двумя десятичными знаками, чтобы не терять точность представления.
result — число; txn_id и prv_txn_id — строки.
JSON — согласованный формат реализации, XML не используется.

Запрос pay проверяет счёт, создаёт APPROVED-пополнение KASPI, увеличивает wallet.money и записывает TOPUP_KASPI одним атомарным действием.
Дата операции в денежном журнале берётся из txn_date (UTC+5), а не из времени получения запроса. Запись содержит исходные txn_id, txn_date, account, признак технического счёта и отдельное received_at — фактическое время получения. Заявка пополнения сохраняет время создания на сервере.
Неуспешная запись журнала откатывает и баланс, и платёж.
Ключ идемпотентности: kaspi:<txn_id>, уникальный в хранилище. Одновременные повторы сериализуются блокировкой БД.

## 6. Повторные запросы и ошибки

Повтор успешного pay с тем же txn_id, account и sum возвращает прежний prv_txn_id, sum и result=0. Нового зачисления нет.
Идентичный повтор остаётся успешным даже если после первого зачисления счёт был заблокирован.
Тот же txn_id с другой суммой или другим account: result=5, исходный платёж не меняется.
После таймаута или временной ошибки повторять исходный pay с тем же txn_id, не создавать новый идентификатор.
Проверка check не подтверждает поступление денег; подтверждение — только result=0 на pay.
При result=5 сначала выяснить причину: некорректные параметры не исправляются повтором без изменения запроса; временная ошибка допускает повтор.

Коды протокола:
0 — счёт найден (check) / платёж успешно зачислен (pay).
1 — счёт не найден или недоступен.
2 — заказ отменён; для кошелька не используется.
3 — заказ уже оплачен; для кошелька не используется, повтор возвращает 0.
4 — платёж в обработке; возможен для уже существующей незавершённой записи.
5 — некорректные параметры, конфликт реквизитов или временная ошибка провайдера; пояснение в comment.

Бизнес-ответы протокола: HTTP 200. Не разрешён IP: HTTP 403. Инфраструктурные 5xx/таймаут означают неопределённый исход; повторить с тем же txn_id.
Таймаут банка по протоколу: 15 секунд. API рассчитан на 10–15 одновременных соединений; финансовая транзакция ограничена 10 секундами, ожидание пула — 2 секундами, ожидание блокировки — 5 секундами.

## 7. Тестовый водитель для сертификации

account: 70000000001
Техническое представление телефона: +70000000001.
Название: Kaspi — технический тестовый водитель.
Это специально выделенный технический идентификатор, не номер реального человека и не номер для SMS/звонков.
Профиль PENDING, приём всех видов поездок отключён. Пароль случайный и не передаётся; вход в приложение для проверки API банку не нужен.
Счёт создаётся скриптом выпуска; при конфликте с существующим пользователем скрипт останавливается и ничего не перезаписывает.
API не имеет параметра demo=true. Запрос pay на технический счёт создаёт запись в той же БД и изменяет его технический баланс. Это не доказательство банковского расчёта: банк отдельно подтверждает режим сертификации/проведения платежей по договору.
Не отправлять тестовые pay на личные номера водителей. Не очищать историю после тестов без отдельного согласования сверки.

Матрица приёмки (с разрешённого IP банка):
1. check технического счёта с фиктивной sum → result=0, баланс прежний.
2. check отсутствующего счёта → result=1.
3. pay на 1.00 KZT с новым txn_id → result=0, баланс +1.00, получен prv_txn_id.
4. Повтор пункта 3 → тот же prv_txn_id, баланс не меняется.
5. 10 одновременных повторов пункта 3 → одно зачисление.
6. Тот же txn_id, sum=2.00 → result=5, баланс прежний.
7. Новый txn_id, неверная дата / сумма 0.00 / отрицательная / больше лимита → result=5.
8. txn_id длиной 18 цифр → обрабатывается без округления.
9. Запрос с неразрешённого IP → HTTP 403.
10. Сверка: txn_id банка ↔ prv_txn_id InterCity ↔ исходные txn_date и сумма в журнале.
Для каждого нового платёжного сценария банк должен выделять новый txn_id. Примеры документа не предназначены для многократного создания разных платежей с одним ID.

## 8. API приложения InterCity

GET /api/wallet/kaspi/instructions
Authorization: Bearer <JWT водителя>. Возвращает available, account, currency=KZT, paymentUrl, bankConnectionReady, message.
Пока банк не выдал ссылку: paymentUrl=null, bankConnectionReady=false. Экран показывает «на подключении» и номер счёта; карта Kassa24 остаётся доступной.
После подключения банка подтверждённую ссылку https://kaspi.kz/... или https://pay.kaspi.kz/... задают в настройке kaspiPaymentUrl. Произвольные домены и ссылки с логином/паролем отклоняются.

GET /api/wallet?currency=KZT
Authorization: Bearer <JWT водителя>. Возвращает money, topups и transactions. После возврата из Kaspi или «Обновить баланс» приложение читает этот API.
Нажатие «я оплатил», закрытие окна или переход по ссылке не зачисляют деньги.

Текущий альтернативный способ: POST /api/wallet/topup-request, JWT водителя, JSON {"amount":500,"currency":"KZT"}. Создаёт онлайн-оплату через Kassa24. Для Kaspi этот endpoint не вызывается.
POST /api/wallet/topups/:id/check — защищённая проверка заявки Kassa24 владельцем; не вызывает pay Kaspi.

## 9. Что передать и согласовать с Kaspi

Передать банку: адрес callback, JSON UTF-8, account regex, поля check/pay, коды, лимиты, тестовый account и эту матрицу приёмки.
Получить от банка: подтверждение услуги InterCity и её наименования в каталоге; подтверждение IP (особенно 197.187.244.108); тестового/боевого режима и расчётов; часового пояса txn_date; deep link услуги и регламента сверок.
Протокол не содержит API получения deep link, API возврата средств, запроса статуса или отмены. Такие методы здесь не выдуманы и должны согласовываться отдельно, если потребуются.
Настройка API не публикует услугу автоматически в приложении Kaspi.kz: каталог, договор и приёмка зависят от банка.

## 10. Примеры curl для команды банка

curl --get 'https://api.intercity.89-207-255-27.sslip.io/api/payments/kaspi' --data-urlencode 'command=check' --data-urlencode 'txn_id=100000000000000001' --data-urlencode 'account=70000000001' --data-urlencode 'sum=200.00'

curl --get 'https://api.intercity.89-207-255-27.sslip.io/api/payments/kaspi' --data-urlencode 'command=pay' --data-urlencode 'txn_id=100000000000000002' --data-urlencode 'txn_date=20261112150000' --data-urlencode 'account=70000000001' --data-urlencode 'sum=500.00'

Запускать с подтверждённого исходного IP банка. С рабочего компьютера или стороннего сервера ожидается 403; это корректная защита, а не ошибка интеграции.
