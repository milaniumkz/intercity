# Межгород: сохранение формы и запрет дублей

Исправлены два воспроизводимых механизма сброса формы:

- У пассажира возврат браузера в активное состояние запускал принудительное обновление GPS даже в частично заполненном межгороде. Оно вызывало очистку адресов, даты и черновика. Автоматическое восстановление GPS теперь ограничено пустой городской подачей; обновление координат не очищает маршрут межгорода. Регрессионный тест падает на прежнем коде и проходит после исправления.
- У водителя повторное быстрое нажатие на город могло дважды закрыть Navigator и вывести со страницы формы. Поиск закрывается однократно, поздние сетевые ответы игнорируются, контроллер освобождается после окончания закрытия окна.

Запрет повторной активной заявки проверяется на сервере: один пользователь, направление «город отправления → город назначения» и выбранный календарный день. Другое время, цена и число мест не создают второй маршрут на тот же день. На другую дату можно создать отдельную заявку; разные направления независимы. Отменённые заявки и отключённые маршруты без оставшихся принятых бронирований не мешают новой публикации. Отключение маршрута не даёт обойти защиту, пока на этот день остаются принятые пассажиры; заявка на другой день разрешена.

Проверка действует для заявок пассажира, маршрутов водителя и старого API водительских поездок. Два водительских API проверяют друг друга. Создание сериализовано блокировкой строки аккаунта внутри транзакции — одновременные запросы не обходят проверку. Конфликт возвращает HTTP 409 и код DUPLICATE_INTERCITY_DEPARTURE с понятным сообщением. Форма при конфликте сохраняется.

Для сравнения дней новые клиенты отправляют UTC-время и смещение выбранной даты. У старых записей неизвестное смещение не выдумывается: поле остаётся NULL, известное смещение зарезервированного водительского маршрута переносится миграцией; для сравнения неизвестного старого дня используется смещение нового запроса. Даты существующих заказов не меняются.

У водительских маршрутов снято старое ограничение одной записи на направление, которое перезаписывало дату. Теперь каждая дата — отдельная запись; бронирования, места, поднятие в топ и идентификаторы старого маршрута сохраняются. Подбор заявок учитывает подходящую дату каждого маршрута и не перекрывает один день другим.

Плановые межгородские заявки OPEN/DRIVER_ASSIGNED не перенаправляют пассажира из новой формы: иначе было невозможно создать заявку на другую дату. Уже начатая поездка и текущие заказы продолжают блокировать создание. Активная поездка имеет приоритет над более новой плановой при определении текущего заказа. Перед фактическим выездом/началом следующей поездки сервер повторно проверяет, что у пассажира нет другой текущей поездки, в той же транзакции с блокировкой аккаунта.

Проверки: сборка backend; общий набор Node (132 успешных, 43 существующих пропуска); пять целевых прогонов с реальной локальной PostgreSQL (23 успешных, один пропуск отдельного currency-стенда). Проверены разные часы одного дня, разные даты, регистр/пробелы/дефисы города, границы дня по смещению, конфликт двух API водителя, две независимые конкурентные транзакции, сохранение старых записей и репетиция SQL-миграции в отдельной откатываемой схеме.

Flutter analyze и release web build. Пять полных прогонов приложения: в каждом 410 успешных тестов и 9 существующих пропусков. Выполнена release-сборка веб-версии. Браузерный тест пять раз имитирует возврат из фона, проверяет сохранение адресов/даты и отсутствие перенаправления из-за плановой заявки. Поиск с двойным нажатием и текст отказа с сохранением формы проверяются отдельными Flutter-тестами. Бизнес-API браузерного теста подменён, production-заказы не создаются.
